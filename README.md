# АОСР — GitHub Cloud (без Supabase)

## Что делает эта версия
- Сохраняет форму локально в браузере и отправляет изменения в `data/state.json` примерно через 2,5 секунды после правки.
- Каждая запись `data/state.json` создаёт отдельный Git-коммит с сообщением `Autosave AOSR data`.
- Загружает данные при подключении, возвращении на вкладку и примерно каждые 90 секунд.
- При конфликте версий повторно получает файл и пытается объединить изменения. Записи журнала `acts`, материалы `reg` и график `sch` получают стабильные идентификаторы и объединяются по `id`; массивы без `id` обрабатываются целиком. Если два устройства одновременно меняют одно и то же поле, применяется локальная версия устройства, которое выполняет успешную запись последним.
- Очистка массива/замена сметы остаётся явной заменой массива, чтобы старые позиции не возвращались при обычной синхронизации.

## Важно о безопасности
GitHub Pages — статический хостинг, поэтому у страницы нет серверной части, которая могла бы скрыть GitHub-токен. В этой версии используется Fine-grained Personal Access Token, ограниченный одним репозиторием и разрешением `Contents: Read and write`. Токен вводится в интерфейсе и хранится только в `sessionStorage` текущей вкладки; он не попадает в HTML, `config.js`, `state.json` или Git-коммиты. Любой JavaScript, исполняемый на этом сайте, технически может получить токен из памяти вкладки, поэтому используйте только собственный репозиторий, не подключайте сторонние скрипты и отключайте токен кнопкой «Отключить» после работы. Для более сильной защиты нужна серверная прослойка (это уже не полностью GitHub Pages-only).

## 1. Опубликовать сайт
1. Распакуйте архив.
2. Загрузите `index.html` в корень вашего GitHub-репозитория (можно заменить старый `index.html`).
3. В настройках репозитория откройте **Settings → Pages** и включите публикацию из нужной ветки и корня (`/(root)`).
4. Дождитесь публикации сайта.

## 2. Создать токен GitHub
1. В GitHub откройте **Settings → Developer settings → Personal access tokens → Fine-grained tokens**.
2. Нажмите **Generate new token**.
3. Выберите срок действия (рекомендуется ограниченный срок).
4. В **Repository access** выберите **Only select repositories** и только репозиторий с сайтом.
5. В **Repository permissions** задайте **Contents: Read and write**. Остальные разрешения не нужны.
6. Создайте токен и скопируйте его. GitHub показывает его один раз. Не вставляйте токен в исходный код и не отправляйте его никому.

## 3. Подключить сайт
1. Откройте опубликованный сайт.
2. В блоке «Облачное хранение GitHub» укажите владельца репозитория (логин пользователя или организации), имя репозитория и ветку (`main`, если не меняли).
3. Вставьте Fine-grained token и нажмите **Подключить и синхронизировать**.
4. При первом подключении страница создаст `data/state.json`; при последующих загрузит его.
5. Повторите подключение на другом устройстве, введя тот же token. Токен в браузерной сессии другого устройства автоматически не переносится.

## 4. Проверка
- Измените поле и подождите около 3 секунд.
- В репозитории откройте `data/state.json`: должно появиться сохранение.
- Откройте **History** файла: каждое сохранение — отдельный коммит.
- Откройте сайт на другом устройстве и подключите тот же репозиторий и token.

## Резервное копирование и откат
История коммитов файла `data/state.json` доступна в GitHub. Для восстановления откройте историю файла, выберите нужный коммит и восстановите его содержимое. Перед ручным восстановлением рекомендуется скачать текущий `state.json`.

## Ограничения
- Сохранение выполняется через GitHub REST API, поэтому нужен интернет и действующий токен.
- Токен хранится в `sessionStorage` и исчезает после закрытия вкладки/сессии; на каждом новом устройстве его нужно ввести.
- Опрос облака выполняется каждые 90 секунд, при возвращении во вкладку и после подключения.
- Синхронизация объединяет записи журнала, материалы и график по стабильным `id`, а также независимые поля объекта. Если два устройства одновременно меняют одно скалярное поле, выигрывает локальная версия устройства, которое успешно записывает данные последним. Массивы без `id` считаются цельными блоками; явная очистка массива имеет приоритет, чтобы удалённые позиции не воскресали.
- В этой реализации нет отдельной серверной блокировки транзакций. При очень частых одновременных правках возможна ситуация, требующая повторной синхронизации. Для одного пользователя обычный сценарий — редактирование на одном устройстве за раз — наиболее надёжен.
